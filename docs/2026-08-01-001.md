# 2026-08-01-001 — Writing XMP, and why ICC is not the same question

Design record for XMP editing in the File info panel, the custom-property grid,
and the per-tab scoped removals. Follows `2026-07-31-001`, which shipped the XMP
and ICC tabs read-only and deferred editing.

Written after the fact from the design conversation that produced it, so it
records what was decided and why rather than the order it was decided in. The
empirical facts in §2 are the expensive part — they were established by probes
against exiv2 0.28.8 and would cost real time to rediscover.

## 1 — The provenance question decides the scope

Whether these values originate from the camera, and therefore whether it makes
sense to add them from an external tool, splits three ways — and the split *is*
the design:

**EXIF is camera-authored.** A capture record: exposure, aperture, ISO, lens,
capture time, GPS fix. Editing it is rewriting history, which is why
`editableTagKeys()` is a deliberate four and not "whatever the tab shows". That
conservatism stays.

**XMP is the opposite.** Adobe designed it in 2001 precisely as the container
for metadata that *downstream tools and people* add. Cameras mostly do not write
it at all (a few write `xmp:Rating`; DNG uses it structurally). Essentially every
XMP packet in the wild came from Lightroom, Bridge, darktable, digiKam, Capture
One, exiftool or a DAM. The properties that matter — `dc:title`,
`dc:description`, `dc:subject` (keywords), `dc:creator`, `dc:rights`,
`xmp:Rating`, `xmp:Label` — are cataloguing fields with no camera origin
whatsoever. Writing XMP from an image browser is the format's designed purpose,
and is better motivated than the EXIF editing this app already shipped.

**ICC is not descriptive metadata at all.** It is a rendering instruction: how to
interpret the pixel numbers. Its origin is the device or the encoder, and it has
no user key/value space — the blob is a fixed structure of spec-defined tag
signatures (`desc`, `wtpt`, `rTRC`, …), not a property bag. "Add a key/value
under ICC" has nothing to implement.

So: **XMP became writable; ICC did not gain key/value editing.** The only ICC
operation offered is removal (§6).

## 2 — What the probes established

Verified 2026-08-01 against exiv2 0.28.8 with throwaway binaries, fixtures
written by Qt (`QImage` + `setColorSpace(SRgb)` + `save()`). Each fact has a
consequence that is still load-bearing in the code:

1. **XMP writes succeed on jpg, png, webp and tiff.** The write gate can be
   wider than EXIF's jpeg/webp — a png can be catalogued.
2. **The embedded ICC profile survives every XMP write**, on all four formats.
3. **Text and LangAlt assignment replaces; array assignment appends.** Replacing
   a keyword list therefore requires erase-then-add, or it grows on every edit.
4. **Empty-string assignment does not delete** — it leaves a present-but-blank
   property. "Empty means remove" needs an explicit `erase()`.
5. **The displayed array form is lossy.** exiv2 joins bag items with `", "`, and
   an item may contain a comma: `{beach, golden hour, "vacation, 2026"}` displays
   identically to four items. This is why the editable API carries `QStringList`
   and never a joined string.
6. **A single language can be cleared without touching the others.** Assigning
   `"lang=x-default "` dropped exactly the x-default entry of a three-language
   `dc:title` and left `ja-JP` and `de-DE` intact. Clearing a title does not
   destroy translations.
7. **`XmpProperties::propertyInfo()` is the registered-vs-custom predicate** —
   non-null for schemas exiv2 knows, null otherwise.
8. **Custom-namespace properties are readable, editable and removable in a
   process that never registered their prefix**: the binding travels in the
   packet's own `xmlns`. They are always `XmpText` — flat and untyped, which is
   what makes them safe to edit as free text where a typed standard property is
   not.
9. **A prefix the file does not already declare fails loudly**: ``No namespace
   info available for XMP prefix `zz'``, and succeeds after `registerNs()`. So
   introducing a namespace needs a URI, and the failure is catchable.
10. **exiv2's iteration order is neither grouped nor lexicographic**, so the
    property list has to sort explicitly.
11. **Each removal is isolable**: `exifData().clear()`, `xmpData().clear()` and
    `clearIccProfile()` each leave the other two kinds intact on jpg/png/webp.
    This isolation is what allows three removal buttons in three tabs.
12. **TIFF is the exception.** Its ICC profile *is* an Exif tag
    (`Exif.Image.InterColorProfile`), and `exifData().clear()` leaves ~15
    structural tags standing because exiv2 must rewrite them to emit a valid
    file. The scopes are not disjoint there, so TIFF is outside every write gate
    — for a reason about scope, not caution.

## 3 — The curated editable set

A fixed list, for the same reason `editableTagKeys()` is one: each key's type has
to be known at compile time, and per fact 5 an array's displayed value cannot
round-trip.

| exiv2 key | XMP type | Label | Editor |
|---|---|---|---|
| `Xmp.dc.title` | LangAlt | Title | line edit |
| `Xmp.dc.description` | LangAlt | Description | line edit |
| `Xmp.dc.creator` | Seq | Author | one per line |
| `Xmp.dc.rights` | LangAlt | Copyright | line edit |
| `Xmp.dc.subject` | Bag | Keywords | one per line |
| `Xmp.xmp.Rating` | text, `-1`–`5` | Rating | line edit, validated |
| `Xmp.xmp.Label` | text | Label | line edit |

LangAlt is edited as `x-default` only; per fact 6 other languages survive both
writes and clears.

## 4 — Standard and custom, and why they differ

The property list below the curated fields splits into two lexicographically
sorted groups:

| | Standard | Custom |
|---|---|---|
| Predicate | `propertyInfo() != nullptr` | `propertyInfo() == nullptr` |
| Type | declared (LangAlt / Seq / Bag / Text) | always `XmpText` |
| In the list | read-only | editable in place, removable |
| Add new | no | yes |

A standard property outside the curated set is shown and not editable: the app
knows its type is not plain text and has no typed editor for it. A custom
property is safe to edit as free text precisely because it has no declared type
to violate. Typing a standard key into the grid is refused with a reason naming
where it *can* be edited.

## 5 — The custom grid

A two-column grid whose last row is always blank; filling it appends a fresh
blank beneath. Blank rows are never written.

| Key | Value | Written as |
|---|---|---|
| empty | empty | nothing — the trailing affordance row |
| empty | non-empty | nothing; the row explains it needs a key |
| non-empty | empty | property with an empty value (legal, and stable per fact 4) |
| non-empty | non-empty | property with its value |

**The key is the delete handle.** Clearing a row's key erases the property;
clearing its value leaves the property present and empty. This differs from the
curated rows, where blanking the value *deletes* — and the two are consistent
under one principle: **whatever field carries the row's identity is what deletes
it.** A curated row has no key cell, so its value is its only handle.

Renaming is erase-old + add-new, because exiv2 has no rename.

Rows commit as a **whole row**, not per field: per-field commit would write a
key-only property the moment focus left the key cell, then rewrite it when the
value arrived. When the typed prefix is unknown, a third cell appears asking for
the namespace URI, and the row stays uncommitted until it is filled — filling
only that cell counts as a change, or the edit that makes the row valid would be
swallowed.

## 6 — Removals: one per tab, scoped to that tab

| Button | Removes | Tab | Gate |
|---|---|---|---|
| Remove all Exif | Exif only | EXIF | jpg, jpeg, webp |
| Remove all XMP | XMP only | XMP | jpg, jpeg, png, webp |
| Remove colour profile | the ICC profile | ICC | jpg, jpeg, png, webp |

Clearing everything is three deliberate acts in three places. "Three" is a
maximum, not a constant: the EXIF tab is hidden for formats exiv2 cannot write
Exif into, so a png offers two.

Each confirmation names its own scope, because "remove all" on its own reads as
"remove everything" whichever tab raised it. The whole-file strip is deliberately
**not** a button in this dialog any more; it remains an `ActionManager` action
reachable by shortcut and menu, which is also the only route that removes Iptc,
since Iptc has no tab.

Assign and convert are **not** offered for ICC: assigning a profile without
converting pixels silently changes every colour, and converting is a re-encode.
Removal is the one ICC operation whose consequence is legible.

Per-row `×` on the custom grid carries no confirmation — the remove toggle that
reveals it is the deliberate act, and a key and value can be retyped. Bulk
removals confirm; single rows do not. That is the line `core.cpp` already drew
for single-tag edits.

## 7 — Button visibility: two axes

- **Hidden** — the button does not belong on this tab, *or* there is nothing for
  it to remove.
- **Disabled** — there is something to remove, but the file cannot be written.

Greying therefore means exactly one thing: *"there is something here, but I
cannot write to this file."* This deliberately changed shipped behaviour, which
previously conflated "nothing to do" with "cannot do it".

The remove toggle resets to off on every retarget: the window is retargeted live
as the selection changes, so a delete mode left on would put an `×` next to rows
nobody has read yet.

## 8 — Defensive caps

Constants in code, not settings — a configurable cap is an invitation to raise it
and meet the pathology it prevents. What cannot be capped is exiv2 parsing the
packet; what can is widget construction, where the cost is.

| Constant | Value | Applies to |
|---|---|---|
| `kMaxXmpRowsDisplayed` | 512 | rows built per XMP list group |
| `kMaxMetadataRowsDisplayed` | 4096 | the EXIF tab's list |
| `kMaxCustomXmpProperties` | 256 | refusing a new custom property |
| `kMaxXmpValueLengthEdited` | 4096 chars | a row being editable at all |
| `kMaxXmpKeyLength` | 256 chars | a key accepted from the grid |

Two row numbers rather than one: XMP properties are authored a handful at a time,
while an Exif dump is machine-generated and a MakerNote-heavy body runs to
hundreds, so a shared 512 would truncate real camera files. (Measured locally:
400 images, max 62 tags — all phone cameras, so that bounds the common case, not
the worst one.) The "thousands of keywords" objection does not apply: keywords are
items inside one `Xmp.dc.subject` bag, a single property, which is not row-capped.

A row whose value exceeds the edit cap is shown **read-only**, not merely elided.
Eliding for display and then committing on focus-out would write the elided text
back and silently truncate real data.

## 9 — Notices

A format that can carry XMP but is outside the write gate says so — *"TIFF
metadata is shown read-only…"* — driven by the gate rather than a hardcoded
format name, so anything later added to the read gate inherits the explanation.
The same notice covers a file in the write gate that is not writable on disk.

## 10 — What is not here

- Assigning or converting ICC profiles (§6).
- Standard properties outside the curated set remain read-only; a typed editor
  for `photoshop:*` or `Iptc4xmpCore` structs is a separate design.
- Iptc has no tab and therefore no scoped button.
- TIFF stays read-only for every kind (fact 12).
