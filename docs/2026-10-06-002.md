## How the answers were reconciled

Answers 2 (async for N images) and 4 (single-file dialog) meet in the middle:
the **existing** dialog drives multi-file runs, interpreted per image.

| Dialog choice | Applied to each selected image |
|---|---|
| Percentage | Same percentage of *that* image's size |
| Absolute W×H, keep aspect on | **Fit within** W×H (aspect kept) |
| Absolute W×H, keep aspect off | Exact W×H (user opted out of aspect) |

The dialog is seeded from the last selected image's header size
(`QImageReader::size()`, no decode). The title says copies are saved.

## Design changes vs -001

| -001 said | Now | Why |
|---|---|---|
| Item 3 mutates the cached image, saves, discards edit | Worker builds its **own** `ImageStatic` from disk; cache never touched | Thread-safe; R2 (wiping a user's unsaved edit) cannot happen |
| Item 1 adds a signal chain | Menu item fires the existing `resize` action; `Core::showResizeDialog` branches on view mode | Item 4 falls out of item 1 for free |
| R1 needs new Exif fixing | Already done by `ImageStatic::save` (Orientation=1, PixelX/YDimension) | Verified at `imagestatic.cpp` metadata block |
| Synchronous like Convert | 1 image sync; >1 on a worker thread, summary toast on finish; second run refused while one is active | Answer 2 |

Shrink only has no UI toggle in v1 (no item 2), so it is always on in the grid
flow: images that would not get smaller are skipped and counted. Upscaling stays
possible in the picture view.
